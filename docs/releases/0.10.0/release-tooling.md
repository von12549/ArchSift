# Reproducible Workbench packaging

The release scripts consume the literal version in `Directory.Build.props` and the approved [build profile](build-profile.json). They do not select a version from filenames or turn an RC into stable by overriding an MSBuild argument. Package identifiers and the `archsift` command remain unchanged. Assembly/file versions are `0.10.0.0`; informational versions include the full SemVer and source commit.

1. Review the release contract, current acceptance and host hash baseline. Use PowerShell 7 without Profiles. Keep source, target repositories and external output directories disjoint. Supply an existing, reviewed offline build source explicitly. Network restore is disabled; the public generic feed is produced from a separate actual consumer closure, not from the private IFX feed.
2. Prepare RID lock changes with `scripts/Publish-LocalZip.ps1 -PrepareLocks -LocalFeed <approved-source> -RunRoot <fresh-external-directory>`. Review the resulting normal and Windows RID lockfiles, source changes and third-party identities. Commit the reviewed inputs with the required agent attribution. Obtain current-head PR CI, merge through the authorized process and verify actual-main CI separately.
3. From the clean committed Windows x64 checkout, run `scripts/Build-WorkbenchRelease.ps1 -OutputRoot <fresh-external-directory> -LocalFeed <approved-source> -ExpectedHostHash <reviewed-hash>`. SDK 10.0.303 and runtime 10.0.11 are required. Each attempt has a new directory; preserve a failed attempt. Never edit a dirty-source manifest to make it appear releasable.
4. Inspect `build-result.json`, the native result, package verification, cold/moved consumer reports, per-command logs and final host checkpoint. The output includes five same-version nupkg files with exact internal dependencies, a self-contained Windows ZIP, matching Setup, a minimal generic offline-feed ZIP, a candidate asset manifest and checksums. The offline feed contains five product packages and the reviewed actual third-party closure, with English guides, schemas and configuration templates. `OFFLINE_FEED.md` explains its scope. SHA256SUMS excludes itself.
5. Complete the remaining regression, security/license, negative, read-only external IFX, lifecycle, independent supported Windows and user-owned UI gates. A successful packaging script is a candidate build, not final release acceptance. The final `acceptance.json` is a separate record binding exact bytes. The native package manifest's candidate status describes its packaging stage and is not rewritten after qualification.
6. After RC gates, change the central literal to stable `0.10.0` and refresh/review both normal and RID locks in a new attributed commit/PR. Verify CI and actual-main identity, build stable afresh and qualify the final stable bytes. Do not rename or relabel RC packages. Prepare the concrete final user review packet before requesting the mandatory independent human answers.
7. Publish only the accepted stable assets and matching tag. Verify anonymous downloads, asset hashes, tagged source archives and cold usage. The user has authorized publication, PRs, CI, merges and fixes; this workflow does not authorize live IFX adoption or package-registry publication.

`Copy-ReleaseDocumentation.ps1` maps curated English guides and generic examples into both downloadable ZIPs. Unbundled source references become fixed-commit GitHub links; relative schema, template and legal links remain local. It records source/payload hashes. `Test-ReleaseDocumentation.ps1` checks those hashes, English authored Markdown and contained local file links. It does not certify prose quality, heading anchors or remote URL availability. Original upstream legal files remain byte-identical. The final review must account for those limits.

`Test-WorkbenchConsumer.ps1` uses package references and normal local-tool restore in fresh external caches. Its synthetic full gate has four cases, including a real ArchUnitNET JSON rule. The moved-source run must preserve the same reviewed logical baseline and policy bytes. These checks do not establish IFX current-source compliance or automatic consumer approval. Actual IFX acceptance has its own read-only snapshot and 493-case baseline.
