## Outcome and baseline

A fresh consumer project should need one project entry, a pinned local-tool manifest and a workspace configuration. On a machine with a compatible installed SDK, that entry should restore ArchSift through normal NuGet mechanisms, initialize external state and start either the portable Launcher or direct Workbench. Users should not have to create several directories, copy a Web installation, set environment variables or maintain an outer startup script. Configuration and diagnostics must explain any missing prerequisite.

The delivered 0.10.1 package already contains CLI and Web, but initialization and IFX-specific preparation currently live in `IFX-New/eng/Start-Workbench.ps1`. The three outer scripts under `D:/IFX-10-Root` supply host-specific paths. The helper requires an explicit approved isolated SDK/runtime, a complete 251-package IFX feed, a cache and pre-existing startup configuration. These IFX acceptance constraints must not become universal product requirements.

## Entry, configuration and package ownership

Use `.archsift/start.ps1` as the single project entry. Its default configuration is the sibling `.archsift/workspace.json`; derive the project root from the entry's location rather than the caller's working directory. `-Config` explicitly selects another workspace configuration. Both Launcher and direct Workbench use this entry with a mode argument; there is no dependency on a script above the project root or on the old `eng/Start-Workbench.ps1` startup chain. The old helper remains part of the recorded 0.10.1 rollback baseline, not the new normal entry.

Proposed IFX layout:

```text
<project>/
  .archsift/
    start.ps1                 # the only normal project startup entry
    workspace.json            # versioned project configuration
    workspace.local.json      # optional ignored host settings
    README.md                 # version-matched usage and file roles
  .config/dotnet-tools.json    # shared standard local-tool manifest, original path
  NuGet.Config                # shared standard NuGet configuration, original path
  global.json                 # project SDK constraints, original path
  architecture/               # existing IFX rules/policies/approvals, original paths
  tests/Architecture/         # existing IFX architecture test source, original path
  eng/                        # existing gate/audit/shared helpers retain their paths
```

The `.archsift/` directory contains the entry, project configuration and usage documentation. No package, extracted Web/runtime, state, cache, generated startup/daily configuration, logs, evidence or reports are written there. Generic new projects may explicitly add versioned `.archsift/rules/`; IFX's existing rules are referenced in place and are not copied, moved or made into a second editable authority. Standard tool/NuGet/SDK files and shared CI/test files are not collected under `.archsift/`. Preserve shared `eng` safety/runtime helpers used by existing gates at their original locations.

Planned normal invocation from the project root is `pwsh -NoProfile -File ./.archsift/start.ps1`; mode, initialization-only and diagnostic options remain available. Absolute invocation from another directory must behave identically. Before invoking dotnet, deliberately use the target project root as the working directory for standard tool-manifest, NuGet and `global.json` resolution; do not change resolver scope just because the entry moved into `.archsift/`.

The entry performs only the pre-package work that cannot execute inside an unrestored package: locate and validate configuration, establish host-safety monitoring, discover an eligible dotnet host, resolve the fixed tool manifest and NuGet settings, perform necessary tool restore, and dispatch to the package. It may create a narrowly owned bootstrap/log/CLI-home area under the resolved external state root. It does not implement rule-library migration, profile/catalog initialization, IFX policy selection or Web lifecycle logic. Ship the entry template with the product; a consumer project copies/adopts it explicitly and subsequently reviews template updates.

The package provides proposed `workspace init`, `workspace doctor`, and `workspace start --mode launcher|workbench` commands. Default `workspace start` runs the idempotent initialization checks, then starts the selected UI. `init` creates/validates owned state and emits resolved settings; `doctor` is diagnostic and does not repair, install or migrate. The project entry exposes initialization-only and doctor actions as well as the normal mode. Preserve existing `ui`, `launch`, analysis and schema-1/schema-2 command contracts for existing consumers.

Use these sources of authority without duplicating standard NuGet concepts:

| File or input | Authority |
| --- | --- |
| `.archsift/workspace.json` | One versioned workspace contract, proposed `kind=archsift-workspace`, `schemaVersion=1`; project identity, target, state, runtime requirements, restore permissions and analysis defaults |
| `.config/dotnet-tools.json` | Exact ArchSift.Cli package version and command; preserve unrelated entries such as dotnet-ef; do not float versions or install globally |
| Standard `NuGet.Config` hierarchy, or explicitly selected config | Sources, mappings, credentials/provider integration and NuGet cache settings; do not copy those settings into a parallel product-specific source list |
| Optional `.archsift/workspace.local.json` | Ignored host-specific override limited to state root, explicit dotnet path, cache path and a standard NuGet config-file path; every selected config still obeys offline/source approvals and cannot weaken runtime mode, SDK floor or IFX policy |
| Existing IFX architecture metadata | Required cases, policies, runtime/package/source approvals and audit requirements; editable workspace settings cannot replace this authority |

Configuration precedence: allowed explicit entry overrides > allowlisted local host settings > project workspace settings > documented defaults. Project policy is a constraint applied after resolution, not another overridable default. Reject unknown/future schemas, duplicate or conflicting identities and invalid paths with precise diagnostics. An explicit invalid configuration or dotnet path fails; do not hide it by silently using a default.

The local-file contract is separately identified by proposed `kind=archsift-workspace-local`, `schemaVersion=1`, with only the allowlisted host settings above in addition to those metadata fields. It is not a complete workspace document and cannot replace the project's gate/runtime/source policy.

Resolve workspace file references and `project.root` against the workspace configuration directory. `project.entry` is relative to the resolved project root. Thus `project.root: ".."` in `.archsift/workspace.json` selects the repository root, and IFX metadata references use `../architecture/...`. Existing startup/daily configuration path semantics remain unchanged. Resolve paths inside NuGet files using NuGet's own rules. For an explicit alternate workspace config, load only its sibling `workspace.local.json` when that exact conventional workspace filename is used, or an explicitly selected local file; do not search legacy locations or silently combine settings from another workspace. Do not expand executable expressions or perform shell interpolation. Report effective non-secret settings and their origin, never credential contents or session tokens. Target-root binding is checked on every start.

Proposed generic configuration at `<project>/.archsift/workspace.json`:

```json
{
  "kind": "archsift-workspace",
  "schemaVersion": 1,
  "project": { "id": "example-project", "root": "..", "entry": "Example.sln" },
  "state": { "root": "C:\\ArchSift-lab" },
  "nuget": { "mode": "configured", "allowNetwork": true, "configFile": null, "cacheDirectory": null },
  "runtime": { "mode": "host", "dotnetPath": null, "minimumSdkVersion": "10.0.0", "allowPrerelease": false },
  "workbench": { "rulesets": [], "build": { "mode": "existing" } }
}
```

This example explicitly permits configured network sources. Offline examples set `mode=offline` and `allowNetwork=false`. The initializer must not silently turn an offline project online. A new generic project is not assigned IFX rules or an analysis/build job automatically. Initialization and UI startup do not build or execute the target application.

IFX uses the same schema with `runtime.mode=approvedExact`, `runtime.approvalFile=../architecture/runtime-approval.json`, offline restore, `nuget.sourceApprovalFile=../architecture/package-source.json`, and `gate.metadataFile=../architecture/portable-gate.json`. The actual machine's ignored local settings select the existing isolated dotnet path, a new external state root/cache and an external standard offline NuGet configuration. This last allowlisted override selects a file, not a parallel custom source list; validate its actual sources/cache against IFX approvals after resolution. The existing project-root `NuGet.Config` currently has no sources, so the IFX example needs that explicit approved offline-config selection before restore. Do not modify or move the root file to make the example work. Generic settings cannot override the IFX enforcement path. Freeze the concrete new-version IFX configuration/feed/cache and migration manifest in UP04 before adoption; example paths do not establish approved new artifacts.

Standalone [configuration examples and deployment instructions](20261024-archsift-unified-package-initialization-examples/README.md) cover generic configured/network use, generic offline use, IFX references at their original paths, ignored host settings and an external standard offline NuGet configuration. They are planning templates, not live configuration and not evidence of an implemented parser. The future project ignore rule is `/.archsift/workspace.local.json`; do not ignore the whole `.archsift/` directory or commit machine paths/credentials accidentally.

The new workspace schema is distinct from the existing **schema-1 run/startup configuration** (`target.root`) and **schema-2 daily-test configuration** (`targetRoot`). Generate those downstream files in external state without changing their meanings or expecting the UI to load the workspace JSON into the daily-test input. Templates/help/errors must identify the correct file for each existing UI operation.

## SDK and runtime compatibility

Honor the requested generic minimum as a numeric stable **SDK version >= 10.0.0**, inclusive, not a string comparison. Actual SDK releases use feature-band versions such as `10.0.100`; do not put the conceptual floor `10.0.0` into `global.json` as an installable SDK selection. Default prerelease SDKs are excluded. A later stable SDK can satisfy the floor, but must also pass framework and tool compatibility checks; no automatic upper bound at SDK 10 is introduced by this plan.

Discovery order is an explicit configured/entry dotnet path, eligible host variables (existing `DOTNET_HOST_PATH` and architecture-appropriate `DOTNET_ROOT` values), then PATH candidates. Environment values are discovery hints, not proofs. Resolve candidates to concrete executable paths, deduplicate them, validate actual architecture and installed SDK/framework output, and record the selected host and decision. Unsupported or unavailable hints may be diagnosed while discovery continues; an explicitly selected host does not silently fall back. Initial interactive qualification remains Windows x64; supporting more SDK versions does not promise ARM64 or Linux Web support.

Use the selected executable for all owned child operations. Check both the SDK actually selected in the command's working context and `global.json`, rather than accepting any entry from `--list-sdks`. Existing project `global.json` is honored and never rewritten. If its effective selection is below the tool floor or unavailable, report the conflict and the required explicit project/tooling setup instead of silently bypassing it. Target builds additionally obey their own SDK/framework/pack requirements.

Framework requirements come from the qualified package's real CLI and Web runtimeconfig files and the supported product contract. The inspected 0.10.1 NuGet CLI requires `Microsoft.NETCore.App 10.0.0`; its embedded Web requires both Core and ASP.NET Core `10.0.0`, subject to normal compatible patch selection. Recheck newly built package bytes. SDK 11 alone without the required .NET 10 frameworks is not sufficient. Do not rewrite package runtimeconfigs or use an inherited major-roll-forward setting to bypass requirements. Generic host mode permits compatible supported patches and records the actual runtime; qualification must establish the advertised minimum combination rather than infer it from a successful newer-SDK build.

IFX retains its stronger exact approval: SDK `10.0.303`, host/Core/ASP.NET `10.0.13`, approved file hashes and existing isolated-root requirements. Host discovery may find candidates, but only a candidate passing that approval can run the IFX gate. `minimumSdkVersion` does not weaken it. Preserve `global.json` (`10.0.300`/latestPatch), runtime-approval bytes and the existing guard against unexpected extra .NET 10 patches for this approved integration. Do not edit shared IFX runtime helpers to make generic host discovery weaken existing gate/audit/build behavior.

No SDK installation, workload installation, global-tool installation or automatic host repair occurs during startup. Missing prerequisites produce actionable diagnostics. If future evidence shows the proposed SDK floor cannot execute the package, report a blocked compatibility claim and fix or revise the design explicitly; do not quietly increase the floor.

## Standard NuGet behavior

Use the supported NuGet/.NET tool restore pipeline. An absent explicit `configFile` means normal configuration hierarchy; an explicit file means .NET's documented `--configfile` semantics, not a hand-merged approximation. Honor package source mapping, disabled sources, proxies and standard credential providers. Do not modify User/Machine NuGet settings or persist credentials in workspace JSON or evidence. Interactive authentication is explicit and cannot hang a noninteractive run.

The manifest supplies the exact tool version. Package restore downloads only missing content through configured and permitted sources; a warm compatible cache can be reused. Do not apply `--no-cache` unconditionally to ordinary startup. Generic mode does not require IFX's 251-package feed. The shipped tool dependencies, the target project's build dependencies and an optional offline distribution feed are distinct closures.

Cache selection honors an explicit workspace/local override passed only to the child; otherwise preserve normal effective `NUGET_PACKAGES` / NuGet configuration / default behavior. Resolve the intended cache before isolating `DOTNET_CLI_HOME`, so isolation does not silently redirect standard cache use. Validate that the cache is outside the target; the restored tool payload normally lives inside that cache, while editable state stays separate from both. Shared cache reuse must use NuGet's locking/completion behavior, not custom extracted Web copies; never clear or repair a shared cache automatically.

Offline mode must make **no package or audit HTTP requests**, including implicit inherited sources, provider discovery or vulnerability lookups. Use a scoped, explicit effective offline configuration and owned cache/HTTP-cache settings; test with HTTP request observation. Credentials and settings from online configuration must not leak into offline evidence. Network mode uses configured sources and normal source mapping; never assume multiple sources represent an ordered fallback list. A missing pinned package is an error, not permission to change source or version.

Keep embedded-Web inventory/version/source validation and require the package's matching Web payload. For IFX, retain independent approved archive hashes, all approved feed identities, restored-file comparisons and corruption/mixed-payload rejection even with a warm cache. A mutable inventory or a cache hit is not an authenticity proof. When a source origin cannot be established from a pre-existing generic cache, record that limitation; do not invent download provenance.

The existing release is published on GitHub Releases; planning did not establish availability of ArchSift.Cli on nuget.org or another registry. HTTP-source acceptance requires actual publication availability or an owned test feed. Registry ownership, package metadata/license readiness, authentication and publication are a separately tracked release task; never claim network install works solely because an offline nupkg exists. Visual Studio's NuGet UI may manage source configuration, but a .NET local tool is still restored/invoked as a tool, not added to the target as a PackageReference that starts a UI during build.

## External state and package initialization

Default Windows state base: `C:/ArchSift-lab`; an explicit configuration/local override can select another absolute directory. Initialize only if writable, without automatic elevation or a silent alternate root. Keep per-user/per-project state separated beneath the base, proposed `users/<user-key>/projects/<project-id>`. Persist a canonical target binding and ownership marker; a reused ID bound to another root requires an explicit reviewed rebind/migration, not automatic adoption. Reject traversal, links/reparse-point escapes and overlaps with target, package payload, feed, runtime or cache roots as applicable.

Within an owned project state, keep `config`, `library`, `reports`, `runs`, `launches`, `backups` and `launcher` as separate children. Existing portable Launcher bootstrap rules still apply: the Launcher root starts absent/empty, and startup configuration/library/reports remain outside that root. The package initializer creates the parent/layout and generated startup configuration; it does not fake Setup receipts or recreate a second executable installation. NuGet owns the executable files; state must never persist an executable selection into an obsolete cache/version.

Repeated initialization is idempotent. Use a per-project lock, a bounded transaction journal, create-new/atomic writes and a versioned marker. Preserve existing editable rules, registry/tombstones/chains, profile selection and reports. Resume an interrupted transaction only when recorded inputs and partial bytes match; unknown nonempty directories remain untouched. Neither `start` nor `doctor` performs a destructive schema migration. An incompatible future marker/schema is a clear error. Config edits are explicit; initialization does not overwrite user changes with template defaults.

Record actual host/tool versions, package/config/approval identities, target root, restore result and lifecycle closeout under external state. Keep secret-free stdout/stderr and original failed-attempt evidence. Preserve existing readiness, loopback/token, cancellation, shutdown and parent-loss ownership behavior. A failed/cancelled run cannot display a previous successful report as current. State/library/history survive a cache clear and subsequent normal restore.
