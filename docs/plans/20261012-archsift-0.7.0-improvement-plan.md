# ArchSift 0.7.0 改进计划

日期：2026-10-12（Australia/Sydney）。状态：**实施已授权；0.7-0 基线与 0.7-1 设计完成，0.7-2 核心证据进行中；尚未构建、升级或发布**。用户授权逐阶段验证后提交和推送，以及后续 PR、合并和发布；真实 IFX 仍遵守人工逐块操作门禁。本计划定义 0.7.0 的四项产品改进及其验收边界，不授权将候选 IFX B 类规则纳入正式策略或 CI 门禁。

## 背景与起点

当前 IFX 安装选择 0.6.0，配置为 `existing / net10.0 / Debug`，未提供程序集清单。用户已将 406 条 B 类候选规则导入独立 chain。该 chain 的[首次报告](../../../IFX-10-Root/ArchSift/reports/0e33886572de4309808cbbec9bceb671/2c6569663f4046d598366ef6c27265d5/b6beed746bf14411b23dbbcfcfa19449/report.json)为 `partial / inconclusive / exit 4`：`assemblyCount=0`、`sourceBound=false`、406 条规则全部 `inconclusive`，每条均报告无源码／构建绑定 manifest、零源类型匹配。零 finding 不能解释为 B 类通过。

即使补交外部 manifest，现有产品也会因 IFX 根目录 `Directory.Build.props` 中的 `$(CI)`、`$(NoWarn)` 等条件／表达式给 105 个项目标记 `Build context contains unevaluated conditions/expressions.`；`AssemblyArtifacts.Existing` 对任一此类项目一概撤销源码绑定。`isolated` 构建也会在复制／构建前拒绝这些声明。因此 0.7.0 的首要目标是**在不把未经核实的 DLL 冒充当前源码证据的前提下，支持经审查的外部构建证据**，使实际 IFX B 类测试有可行路径。现行 B 类覆盖和夹具限制见[IFX B 类计划](../../../IFX-10-Root/docs/plans/20261012-archsift-ifx-class-b-rule-plan.md)。

产品起点已核对：交接时本地 `main` 与其缓存的 `origin/main` 仍为 0.5.0 发布文档提交 `57cc4c7`，这是本地未同步；0.6.0 已通过 [PR #3](https://github.com/von12549/ArchSift/pull/3) 合并，产品合并提交为 `b80de2a55e85a80d1ea23f09829ee4b00ecde9d6`。2026-10-12 按用户要求获取远端更新，将本地 `main` 快进至含发布回验资料的 `4ca2a5fc485b28e3aaf4fadd2223bed378d56b03`，并从该提交创建 `codex/archsift-0.7.0`；用户授权将计划改动作为新分支首个提交，产品实施、推送和发布尚未授权。

正式 0.6.0 的冻结产品源码为 `de222c2462e182191b2f71499421bfe086ea7bab`；本地发布／验收记录和 IFX 已选安装的 `package-manifest.json` 均指向该提交。安装 manifest 实际 SHA-256 为 `a70f55859cf276ea786df2e68fcae4599cacc7c62cca9fcde20d27d6655f5e2b`，与发布记录一致；`install.json` 记录的 ZIP SHA-256 为 `64af0fb70ea8548b99373151c7005c15b0365784d8faedd3890989d3d040a560`，亦与发布记录一致。本次未重验完整 647 项安装载荷或重跑发布验收；实施前仍须冻结旧契约、配置、库、chain 和报告样本，补齐完整载荷核验。历史证据保持原字节。

## 0.7.0 范围与验收

| 工作包 | 用户可见结果 | 必须满足的验收重点 |
| --- | --- | --- |
| 0.7-A：外部构建证据 | 对有条件／表达式的 IFX 项目，可提交经过审查且与当前源码绑定的程序集证据；B 类不再因笼统的“未求值表达式”一律失去绑定 | 仅完整且可复核的来源、构建输入、上下文、DLL 和依赖闭包获得可判定结果；缺失、过期或矛盾证据保持 `inconclusive`／`error` |
| 0.7-B：Ruleset／Chain Create From | 从已保存对象复制成独立草稿，填写新的 Ruleset ID／文件名或 Chain ID，修改版本、描述、规则／条目后再保存 | 原对象字节与引用不变；新对象使用独立身份；冲突和双击不会覆盖现有对象 |
| 0.7-C：Rule results 排序 | Results 中按 `Rule` 或 `Result` 升／降序查看规则结果，包括单 Ruleset 与 Chain 子报告 | 只改变页面显示顺序；JSON／HTML／SARIF 的稳定结果顺序和身份不变 |
| 0.7-D：Launcher 关闭反馈 | `Close launcher` 点击后显示确认／关闭进度，按钮进入不可重复提交状态，服务关闭结果在页面可辨识 | 区分“请求已接受”“服务端点已退出”“关闭失败／超时”；活动工作台、未保存修改和 job 的现有保护不被绕开 |

### 0.7-A：可信程序集证据

1. **冻结证据契约。** 在现有 `assembly-manifest` 基础上设计向后兼容的外部构建证据版本或扩展。记录构建前后源码输入身份、实际读取的构建输入及内容哈希、MSBuild 条件所依赖的已求值属性／环境、SDK／TFM／Configuration、命令与构建日志身份、项目→程序集映射、DLL SHA-256、生成器／自定义任务／导入路径及依赖闭包。声明哪些事实由工具直接复核、哪些属于操作员审查／外部构建证明；报告不得把外部证明写成工具自行重建的证明。清单、日志和产物放在目标源码根外。
2. **提供可操作的获取流程。** 0.7.0 应提供明确的外部取证／清单生成与校验入口，或随产品交付可复核的操作员流程；不能要求用户猜测 `InputIdentity`、`BuildInputIdentity` 的哈希算法并手填 JSON。现有 `isolated` 自动生成 manifest 的路径继续可用，但对 IFX 的表达式和自定义构建不得靠跳过检查强行启用。外部取证不得默认运行目标应用，也不得隐式联网或将输出写入 IFX 源码树。
3. **针对性替代笼统拒绝。** 保留项目声明扫描的保守限制；只有提供充分、当前且经核对的外部构建证据时，才允许这些限制由具体已求值事实解除。核验应覆盖本次发现的 105 个项目，尤其是根 `Directory.Build.props` 的条件／属性；不能通过删除 IFX 正常构建声明或仅把 `Build context` 文案从报告中隐藏来获得绑定。未知条件、未追踪导入、生成器／任务的输入或外部路径继续给出具体限制，不把单一清单哈希当成完整构建证明。
4. **验证及报告语义。** 反例至少包括源码或 props 修改、条件输入变化、不同 SDK／TFM／Configuration、旧 DLL、DLL 哈希／PE 元数据不符、缺一个第一方项目或依赖 DLL、闭包版本／token 冲突、零源类型匹配、审查证据缺页、构建中途失败。任何一种都不能报告当前源码 `pass`。保留原始 DLL finding 与当前源码结论的区分。正例用独立、可控的合成项目先证明条件表达式与构建绑定；然后才安排真实 IFX 操作员取证，核对至少 B01–B05/B07 的代表性正反夹具和当前 IFX 报告。
5. **范围界定。** 本包不承诺任意 MSBuild 脚本的通用安全求值，也不自动放行 custom target／package script。若正式设计发现某个 IFX 输入无法完整取证，应列出具体项目与原因并保持 `inconclusive`，不得降低绑定标准来满足发布日期。

### 0.7-B：Ruleset 与 Chain Create From

- 在已保存的 Ruleset 卡片和 Chain 卡片提供 `Create From`。从**已保存字节**创建新草稿，不依赖未保存编辑器状态；若当前编辑器有未保存改动，先用既有保护流程让用户决定，取消则不改变当前草稿。
- Ruleset 草稿复制规则、例外、描述和版本；新 `ruleset.id` 与 `.json` 文件名必须显式填写且与库中现有值不同。内部 rule ID、例外所指 rule ID 先保留，允许用户随后修改，保存时照旧校验唯一性与引用；提示若将源和副本放进同一 legacy composed `verify`，重复 rule ID 可能冲突。保存生成新的库 `entryId`，不重写原文件或原 chain 引用。
- Chain 草稿复制版本、描述和**有序的稳定 entryId 引用**；`chain.id` 在副本中可编辑，新 ID 必须不同且未占用。现有 chain 编辑时 ID 仍作为身份固定。源 chain 若含缺失／已删除 ruleset，副本必须显式显示这些引用并要求修复或清楚保留其缺失语义，绝不按文件名自动重绑。
- 服务端提供创建专用的无覆盖写入语义或等价原子检查；仅前端校验不足以防并发、重复点击、大小写碰撞与路径冲突。失败后原对象、新对象和库 registry 均应保持一致。复制本身不执行验证，也不修改历史报告或旧 chain snapshot。
- 验收：406 条 B 类规则集复制、重命名与保存可用；A 类 chain 复制后可改 ID 与顺序，而旧 chain 的 ID、entryIds、规则字节及验证行为不变；编辑中取消、冲突、失效条目、双击与键盘操作均有明确结果。中英文 UI 文案同步。

### 0.7-C：Results 中规则结果排序

- 对单 Ruleset 的 `Rule results` 表和 Chain 各子报告的对应表，提供 `Rule`、`Result` 两个可见排序控制，支持升序／降序及返回报告默认顺序。排序状态可按当前结果视图维护；切换当前／历史任务或不同子报告不得把上一个任务的排序误用为结论。
- `Rule` 按完整可见 rule ID 做稳定、可预测的排序；`Result` 使用明确状态顺序（建议 violation → error → inconclusive → pass → not-applicable，反向为降序），同状态以 rule ID、原行序打破平局。状态顺序和方向须在 UI 可见，不依赖中文／英文标签的字典序。
- 表头按钮或等价控件支持键盘、焦点、`aria-sort`／状态说明；保留行内 Matched、Limitations 与对应规则的关系。排序只作用于渲染副本，不修改 `ruleResults` 数组、报告文件、summary、finding、稳定 ID 或下载内容。大表（至少 406 行）在桌面和窄屏仍可使用。

### 0.7-D：Launcher 关闭状态

- `Close launcher` 在有活动工作台或未保存编辑时沿用现有会话保护：活动 job 拒绝关闭；未保存内容须明确审阅，用户取消后保持可操作。没有活动会话时也要给出操作确认或同等清晰的关闭意图反馈。
- 确认后立即显示 `Closing…`／`正在关闭…`，禁用关闭按钮和会产生竞争的启动／注册操作；重复点击只对应一次请求。API 拒绝或网络失败时恢复可操作状态并展示错误，不显示“已关闭”。
- 服务端接受请求后，页面显示“关闭请求已接受”；在可观测的本地服务端点退出后再显示“Launcher 已关闭，可以关闭此页”。服务端点失联但无法确认完整进程退出时使用谨慎文案。验收另以 CLI exit、精确 owned 进程及监听退出为客观证据；页面提示不得用一个已收到的 HTTP 200 冒充这些收尾事实。
- 中英文、键盘与屏幕阅读器状态播报、刷新／返回的终态显示均纳入 UI 回归。关闭不修改持久 PATH、配置或用户规则。
