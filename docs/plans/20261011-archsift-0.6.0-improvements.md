## Launcher and profile selection

**0.5.0 baseline.** CLI ui --config/Web load config before page startup; missing/invalid/unsafe files prevent UI. Setup install.json protects one ConfigPath/library with backup/rollback. A dropdown inside Workbench cannot solve config-free startup, and another JSON does not automatically gain protection.

**Proposed flow.** Separate local launcher independent of target config reads verified selected version, lists explicitly registered/user-chosen profiles with canonical full path, root/entry/output/library, valid/missing/invalid and managed status. Keep same-name/equal-byte copies separate, no silent filename/mtime/history choice. Allow locating JSON or reviewed creation outside target repos. Validate schema/paths/version before private-token loopback launch. Workbench always shows profile name/full path.

**Lifecycle.** Launcher stays alive owning UI child, offers reopen/safe shutdown; browser-tab close is not server exit. No URL/token logs/shortcuts/catalog. Resolve active jobs/unsaved edits/service exit before switching; no old results/library/state leakage. Keep explicit ui --config. Shortcuts need no PATH/Profile/env/services/autostart changes.

**Installation design gate.** Freeze registration location, display/path identity, default/recent choice and managed/external boundaries. Original proposal recommended managed catalog/config/library in reviewed install/backup contracts; external protection must be explicit. Define legacy 0.5.0 compatibility and missing/conflicting/edited/incompatible profiles across inspect/upgrade/rollback/startup. No Setup schema change or arbitrary JSON auto-repair before freezing.
