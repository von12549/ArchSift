## Scope and product decisions

1. **English is the default UI language; Chinese remains selectable.** Localize navigation, forms, validation errors, job states, coverage explanations, download labels, help, and safe shutdown. Keep machine field names, status codes, CLI commands, JSON schema keys, and rule type identifiers stable. The selector can persist locally in the browser; missing translations fall back to English. Locale must not affect analysis semantics or report identity.
2. **Current product documentation and product-generated prose are English.** Update README, CLI/rules/build/changes/reports guidance, UI help, release notes, generated Markdown, HTML, SARIF human-readable messages, and tool-authored JSON messages. Preserve user-authored IDs, descriptions, exception reasons, paths, and source text exactly as entered; never machine-translate policy content. Keep historical acceptance records unchanged. A short Chinese quick-start may remain as an explicitly localized companion, not the authoritative contract.
3. **IFX classification C, D, and E are `DEFER` and outside 0.4.0 coverage.** The [classification reference](../../../IFX-10-Root/docs/plans/20261007-archsift-ifx-rule-classification-reference.md) assigns A to declaration rules and B to some compiled-dependency checks. 0.4.0 improves management and orchestration of existing A/B checks; it adds no method/member/protocol static rules (C), runtime proof (D), or approval/governance enforcement (E). Existing B checks remain conditional on trustworthy source-bound assemblies. No result may claim C/D/E or complete IFX protection.
4. **A chain is ordered orchestration, not rule precedence or policy inheritance.** The user chooses one or more rulesets already present in the workbench library, can add/remove/reorder entries, and can edit chain metadata. Each entry runs independently against one immutable target/build input identity and its own frozen ruleset bytes. Reordering changes run and display order only; it cannot change allow/deny meaning, exception attribution, or a finding's status. Existing `verify` with several `config.rulesets` paths remains a composed single-report operation with its existing global rule-ID and cross-file checks.
5. **Continue independent chain entries after a child `partial` result or child ruleset/configuration error.** Preserve the child's limitation or error in the summary and attempt later entries. A missing/invalid target or unsafe global output location prevents all entries; cancellation stops remaining entries and records which completed. This decision was confirmed by the user during planning.

Pair color with explicit text labels and, where useful, icons or borders; retain readable contrast and visible keyboard focus. ## Ruleset JSON import and export (0.4-C1)

- Provide an **Import Ruleset** action in the ruleset library. The operator selects a local `.json` ruleset file. Validate the existing ruleset schema and semantic contract before registering it, then copy it into the configured external `rulesDirectory`; never write into the analyzed target. Show the imported ID, version, filename, and SHA-256. Do not fetch remote URLs.
- Provide an **Export JSON** action on every saved ruleset card. Download that ruleset's current saved JSON file, including its rules and exceptions, as a reusable `.json` file. Export is independent of the active target and must not serialize an unsaved editor draft. Keep **Export Markdown** as a separate, read-only documentation projection.
- An invalid file or filename/ruleset-ID conflict leaves the library unchanged and returns a precise English error. Default conflict handling is **reject**; any future replace action needs explicit confirmation, a recoverable prior version, and review of affected chains. Exported JSON must import again with the same rule semantics and content hash; document whether UTF-8 BOM is retained as part of exact-byte export.

## Ruleset cards and workbench behavior (0.4-C2)

- Replace the left-side global **Verify Rules** action with two explicit surfaces: a **Verify** button on each ruleset card and a **Verify Chain** button on each chain card. Keep project discovery, changes, candidate drafting, cancellation, and safe shutdown discoverable. A ruleset card expands to show ID, version, description, file identity/hash, enabled rule count, rule list, exceptions, and edit actions. Editing continues to use the existing validated JSON contract and must not silently save draft changes before a run.
- A ruleset-card Verify job selects **exactly that saved ruleset**, even when the startup config lists others. It freezes target, rule file hash, build inputs, output root, and target kind before execution. The job gets a unique report directory and JSON/HTML/SARIF outputs. Other cards and an unsaved editor draft have no effect. A failed run must never show a previous card's count or downloads as current.
- Chains are stored as separate versioned JSON documents outside the target and reference library rulesets by stable library entry ID; they do not copy or inline rules. The UI lists them as expandable cards with add/edit/delete/reorder and Verify actions. New chain entries must select an existing library ruleset, and a chain cannot include the same ruleset twice by default. Each new run uses the latest **saved** bytes of that entry and records their hash; unsaved edits have no effect. Deleting a referenced ruleset does **not** delete its chain entry or disable Verify Chain: the card shows a visible missing-ruleset warning, and the chain remains runnable. Importing a same-name file does not silently reconnect a deleted entry; reconnection is an explicit chain edit. Chain changes are validated and saved atomically.

## Chain report contract

Before starting, record an immutable chain snapshot: chain ID/version, ordered library entry IDs, each source path, available ruleset ID/version/SHA-256, one target/build input identity, build mode, TFM, configuration, output location, and selected target kind. Keep the saved reference of any missing ruleset in that snapshot without inventing current file bytes or a hash. Capture the target/build inputs once or verify exact byte identity across entries; a global input drift stops further analysis and marks remaining entries as affected, rather than silently mixing different source states. Put one child run and its independent `report.json`, `report.html`, and `report.sarif` under a unique chain-run directory for every child that reaches analysis. A missing or invalid child ruleset produces its own clearly typed diagnostic JSON/HTML/SARIF artifacts with no invented rule results. Continue with later entries and do not reuse an older report to satisfy the missing entry.

Generate one chain summary in JSON, HTML, and SARIF. The summary links each child report/error, preserves ordered entry identity and source hashes, presents counts and findings per ruleset, and clearly separates **execution status**, **policy compliance**, **rule results**, **coverage limitations**, and **source binding**. It does not sum repeated project counts as if they were distinct projects. It does not deduplicate different ruleset findings into one policy decision. Rule identities in the summary are qualified by chain entry so independently run files with the same rule ID cannot collide; this does not relax the existing composed-verify duplicate-ID rule.

Expose the same chain execution service through the UI card and a CLI chain-verify command (planned form: `archsift chain verify --config config.json --chain chain.json`). Keep the existing CLI `verify --config` behavior for composed rulesets. External ruleset files named in `config.rulesets` remain valid for that legacy CLI path; the UI shows files outside the managed library as external/read-only and requires an explicit Import action before a chain can select them. No external file is copied or enrolled silently.

Aggregation is conservative: any effective violation makes chain compliance `noncompliant`; otherwise any missing ruleset, child error, or inconclusive child makes it `inconclusive`; otherwise a chain with at least one compliant child and only other not-applicable children is `compliant`; an all-not-applicable chain is `not-applicable`. Execution remains `partial` if any completed child is partial, any child fails or is missing, or any planned child is skipped. A `partial / compliant` chain is possible when all child policy results are compliant but coverage is limited; it must visibly say what was **not** covered. A cancelled chain retains completed child reports and a cancelled summary, with remaining entries marked skipped. The chain summary has its own schema, leaving existing analysis/comparison report schemas unchanged. Overall exit codes follow the current CLI categories: 0 for fully completed, 2 for global configuration rejection before child execution, 3 for global execution failure, 4 for a partial/inconclusive chain, and 130 for cancellation; a child error that does not halt the chain is recorded per entry and makes the overall result partial rather than discarding later results. Summary SARIF may include only actual rule findings as results; missing/invalid entry diagnostics must be distinct tool/execution notifications, never fabricated findings. Freeze exact fields, filenames, and official SARIF-schema validation examples in 0.4-A before implementation.

## D1–D6 decisions accepted for 0.4.0

The user accepted all six recommended directions on 2026-10-09. These are product decisions, not pending questions. 0.4-A still has engineering work to freeze exact JSON schemas, filenames, CLI option names, and schema-valid SARIF examples before implementation.

| ID | Accepted direction |
| --- | --- |
| D1 — reference identity | Chain entries use stable library entry IDs and the latest **saved** bytes at each new run, with the exact hash recorded. Deletion leaves a dangling entry; importing a same-name ruleset does not silently rebind it. An explicit chain edit reconnects it. |
| D2 — per-entry failure artifact | A missing or invalid ruleset gets its own clearly typed diagnostic JSON/HTML/SARIF artifacts and a summary entry, with no invented analysis finding. Entries that reach analysis retain normal independent reports. |
| D3 — non-UI entry point | The same chain is verifiable through CLI and UI. CLI chain verification is distinct from existing composed multi-file `verify`, which remains compatible. |
| D4 — target consistency | All entries must use one immutable target/build input identity. Capture once or prove exact byte equality throughout; global drift stops further analysis and is reported instead of mixing states. |
| D5 — aggregate contract | Use a separate chain-summary schema and conservative status roll-up; keep execution, compliance, rule results, and coverage distinct. Apply existing exit-code categories, report an all-not-applicable chain as `not-applicable`, and put actual findings and execution diagnostics in distinct SARIF roles. Freeze detailed schema examples in 0.4-A. |
| D6 — external ruleset paths | Preserve external `config.rulesets` paths for legacy CLI verification. Show them as external/read-only in UI, never silently copy/import them, and require explicit import into the managed library before chain selection. |

Other fixed defaults: the UI locale does not alter report bytes; generated tool-authored text stays English while user-authored policy text is preserved; import conflicts reject without mutation; no overwrite workflow is required for 0.4.0; historical Chinese acceptance evidence is retained unchanged. Independent chain verification is an audit roll-up, not a merged rule-precedence engine. IFX policy adoption and test-project allowlists remain separate IFX owner decisions.
