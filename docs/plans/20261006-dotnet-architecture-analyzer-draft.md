## 目的与产品定位

建立一个独立的本地 .NET 项目分析工具。用户选择目标和可选规则集，工具读取项目、源码及必要的编译产物，发现依赖关系、执行规则检查，输出可追溯的分析报告。CLI、配置文件和 UI 使用同一个分析核心。

项目分析器在没有规则集时仍能工作；项目验证器在指定规则集后运行；变更验证器比较两个代码状态的检查结果。自然语言 Plan 的影响判断和数据库专项分析延期。CI 可以运行验证并发布报告，默认不因规则违规阻断。

本计划用于讨论产品和工程边界。现阶段交付为 draft 文档与问题清单；正式化后形成独立的实施计划。独立仓库创建、代码迁移和实现不属于当前文档交付。

## 建议的核心结构

```text
CLI / Local UI
       │
       ▼
统一分析服务
       ├── 运行配置与规则验证
       ├── 输入身份与扫描范围
       ├── 项目及包模型
       ├── 源码检查
       ├── 构建产物检查与 ArchUnitNET
       ├── 规则求值
       ├── 前后结果比较
       └── 报告生成
```

建议使用 .NET 类库实现核心、.NET CLI 提供运行入口，ArchUnitNET 通过独立适配层接入。保留现有算法和样例，逐步摆脱 PowerShell Stage 上下文作为核心内部协议。具体 SDK、UI 技术和首发平台见待定问题。

新核心不会依赖 Guard 的 onboarding、Profile 审批、promotion、composition、短期 safety proof 或 protected 判定。配置生效依靠版本化输入和明确参数，不新增另一套授权流程。

默认配置文件只表达目标、规则文件、构建输入、输出及运行选项；规则文件只表达约束，避免将机器绝对路径写入可移植规则。CLI、配置、UI 的优先级需要在契约中固定并显示最终生效值。建议顺序为显式 CLI/UI 输入覆盖配置，再使用文档化默认值。

## 规则集与模板建议

工具实现有限的规则类型；用户通过 JSON 模板创建实例。每个规则集有 schemaVersion、稳定 ID、版本、描述与规则数组；每条规则至少有 ID、类型、enabled、scope、parameters、severity、reason。

scope 用项目相对路径、程序集、命名空间或类型选择器表达。匹配方式明确区分精确值、glob 和正则；不将同一个字符串隐式解释为多种语法。模板提供有效样例、字段说明和不支持情形。

多个规则集组合时报告实际顺序、身份和哈希；重复规则 ID 和冲突定义默认报配置错误。Markdown 由 JSON 自动生成，包含来源哈希与版本；编辑 Markdown 不改变执行规则。UI 保存 JSON 后重新生成阅读版本。

候选首期类型如下，最终清单由 Q06 定案。

| 类型 | 典型约束 | 检查依据 |
| --- | --- | --- |
| project-reference | Domain 项目不得引用 Infrastructure 项目 | 声明或求值后的项目引用 |
| graph-integrity | 项目引用可解析；范围内项目被清点 | 项目清单与引用图 |
| target-framework | 仅允许指定目标框架 | 声明或求值后的框架 |
| nuget-denylist | 禁止包 ID 或指定版本范围 | 直接声明或已解析包图 |
| type-dependency | 某命名空间类型不得依赖另一命名空间类型 | ArchUnitNET 程序集模型 |
| implementation-location | 接口实现归属指定程序集与命名空间 | ArchUnitNET 与必要补充 |
| naming | 项目、程序集、类型或源码文件符合命名约束 | 项目模型、ArchUnitNET 或 Roslyn |

项目分析器生成草稿时分别展示“当前事实”“建议规则”“需要人类决定的规则”。现有依赖不是自动允许清单；用户仍需决定哪些关系应允许或禁止。

## 分析范围与输入身份

项目图必须明确描述范围，而不使用无条件的“完整”承诺。输出列出发现项目、入口 solution、外部引用、条件或无法解析项、所用 TFM/Configuration 以及排除项。声明图与求值图采用不同标识，避免把原始 XML 读取等同于 MSBuild 实际结果。

相关源码、项目文件、规则、构建参数和程序集哈希形成一次运行的输入身份。机器路径用于本地定位，不充当跨机器项目身份。相对路径、内容哈希与可选 Git commit/tree 用于可移植报告。

所有分析阶段共享输入选择机制，并区分源码输入、构建输入和生成证据。IDE 缓存和普通生成目录不应使源码报告失效。自定义 imports、生成源码和 repository 外部构建输入必须明确纳入或标记未支持；不能一刀切忽略所有非源码文件。

运行开始与结束验证相关输入，运行中变化则说明具体原因。编辑器正常开启不构成拒绝条件。报告目录和工具临时产物排除在输入身份之外；输出的核心 findings 在相同输入下保持排序和身份稳定，时间、耗时、机器路径等运行元数据不要求字节一致。

## 构建产物与分析可信度

建议区分使用已有产物和显式生成产物两种模式。未启用构建时不静默执行 build/restore；启用后展示实际构建范围、配置与 restore/network 行为。

已有 DLL 可以得到针对这些 DLL 的报告。只有来源清单足以绑定当前源码、项目范围、SDK、TFM、Configuration、规则和程序集哈希时，才将程序集结果合并为当前源码的验证结论。仅靠文件修改时间不足以证明产物新鲜。

工具生成产物时，采用显式临时目录与隔离子进程；构建会执行项目定义的 MSBuild 行为，隔离目录与环境不能冒充完整安全沙箱。具体构建模式、包缓存和网络权限由 Q08 定案。

编译失败保留已完成的项目模型检查，所依赖的程序集规则返回无法判定，并记录运行错误；整体不得显示完全合规。不同 TFM、Configuration 和构建模式的结果不直接视为等价。

ArchUnitNET 基于编译产物；官方建议 Debug 以减少优化导致的依赖缺失，但仍需针对选定规则验证具体行为。[官方 README](https://github.com/TNG/ArchUnitNET/blob/main/README.md)、[已知构建配置限制](https://archunitnet.readthedocs.io/en/latest/limitations/debug_artifacts/)。

## 报告与变更验证建议

报告包含 toolVersion、reportSchemaVersion、运行类型、源码身份、规则身份、扫描范围、构建上下文、分析引擎版本、逐规则结果、findings、coverage、未支持项和执行错误。每个 finding 包含稳定身份、规则 ID、主体、相对位置或类型证据、解释和所需上下文。

总体合规只在全部启用且适用的规则完成检查并通过时成立。severity 与执行状态分别表达；不能因默认不阻断 CI 就将违规降格成通过。建议全规则不适用、选择器零匹配和部分覆盖均显示明确的汇总说明。

变更验证的两个输入分别为明确基线与目标状态。第一阶段支持最终状态比较，不承诺逐 commit 中间状态验证。暂存区、工作区、未跟踪源码和指定 commit range 分别标识，默认范围由 Q10 定案。

前后两端使用相同规则集比较，得到新增、既有与已解决问题。基线无法分析时只提供目标状态结果，不能推断新增。规则变更单独标注；规则移除或范围缩小不能冒充源码问题已修复。第一版可全量运行两端，后续再优化增量。

CI 默认在存在 findings 时成功生成 artifact；配置错误、工具失败和无法完成运行返回不同执行状态。未来显式开启 fail-on 时才按选择的违规条件返回失败；集成不自动变更远程保护策略。

## 首个完整版本验收草案

1. 无规则集可分析受支持目标，发现项目、引用和框架，明确范围及未解析项。
2. JSON 校验、UI 编辑、CLI 运行与 Markdown 投影对同一规则语义一致；重复或无效规则不会执行。
3. 首期每类规则具有 clean、violating、missing/unsupported fixture；至少一类类型依赖在真实编译产物上经 ArchUnitNET 验证。
4. 缺少 DLL、过期 DLL、未解析引用、零匹配、配置错误和编译失败均有准确状态，覆盖不足不变成通过。
5. 输出含输入与规则身份、引擎及构建上下文、可定位证据；相同核心输入的 findings 一致。
6. VS Code 和 Visual Studio 正常开启时，IDE 产物不会造成无关失效；运行中保存相关源码时能识别输入变化。
7. 无持久环境修改，报告及构建输出在明确目录；新入口不要求八步 onboarding 或手工 hash 操作。
8. 操作者可独立完成配置、运行和理解结果，能分辨违规与无法判定；建议沿用理解信心至少 4/5 且最高 L2 的要求，具体测试方法由 Q13 定案。
9. IFX 真实样例与构造违规样例均形成可复查报告。现场集成遵循当前人工操作规则，每次一块已审查命令后等待结果。
10. 性能与首发平台验收采用 Q03/Q13 冻结的环境和预算；当前没有虚构性能达标结论。

| Q07 | NuGet 禁止列表覆盖 | 首期检查直接声明及可解析的中央版本；包 ID 大小写不敏感；包 ID 为先，版本范围和传递依赖随后加入；不自动联网 | 解析、版本比较与 restore 行为 |
| Q08 | 已有产物可信度、构建和网络 | 默认已有产物模式；未能绑定源码时只作程序集报告；提供显式隔离构建选项；restore 默认不联网，确需网络由用户配置；默认 Debug，记录 TFM/SDK/参数；缓存为可删除本地缓存 | ArchUnitNET 的输入正确性和运行成本 |
| Q09 | UI 类型及配置编辑范围 | 本机 loopback Web UI，.NET 后端；模板表单编辑 JSON，可导出只读 Markdown；MVP 无账号、远程服务或插件市场 | 安装体验和前后端工作量 |
| Q10 | 变更验证默认范围 | 默认 HEAD 与当前工作区（含暂存、未暂存和选定未跟踪源码）；支持明确 base..head；最终状态比较；不自动 fetch、不逐 commit 验证 | 避免“未提交 commits”的歧义 |
| Q11 | 例外、历史违规、零匹配与规则集组合 | 例外有规则 ID、范围和理由；历史 findings 用报告比较，不自动豁免；零匹配默认无法判定，显式允许为空才不适用；重复 ID/冲突报错 | 防止空通过、基线掩盖和隐式覆盖 |
| Q12 | 报告、语言和退出语义 | JSON 与 HTML 首发，SARIF 第二阶段；固定英文机器字段，中文可读界面优先；违规默认 exit 0，配置/运行错误非零，部分无法判定另设代码；未来 fail-on 显式启用 | CI 可观察性、报告契约及本地体验 |
| Q13 | 验收样例、人工步骤、性能与上限 | IFX 与独立 fixture 为首批；保留人工现场集成规则；以独立操作员 4/5、最高 L2 验收；性能先测量，再冻结预算，不设猜测数字 | 正式计划的测试入口与可量化完成标准 |
| Q14 | 发布方式、许可证及旧 Guard 维护范围 | 首个版本只做本地 ZIP，NuGet tool 发布随后；迁移前核对来源及第三方许可证；旧 Guard 暂停新功能，旧 UI 缺陷另列维护任务 | 分发、迁移义务和双项目维护成本 |

Q 项可通过选择明确 defer 关闭，但必须写清移出的功能、当前报告限制和重新评估条件。MVP 核心能力不能全部 defer：至少一个 ArchUnitNET 规则、CLI、简洁 UI、规则模板和报告仍必须可验收。

## 正式化条件与操作

当 Q01 至 Q14 全部 CLOSED（DECIDED 或明确 DEFERRED）后，整理决议并检查交付阶段、范围和验收之间的冲突。工程依赖版本、来源基准及发布身份在正式计划中冻结。

正式化包括：采用最终名称；将建议值替换为确定决议；固定规则和报告契约；列出实际仓库结构、具体任务依赖、验证入口、运行与输出路径、交付方式和完成标准；记录 defer 清单。保留本 draft 作为讨论历史，正式计划另存为 `<日期>-<最终名称>-implementation-plan.md` 并链接来源。

如果仍有 OPEN 项，则继续修订 draft，不将文件改标为正式计划。不采用 Guard 的旧执行计划 schema 作为新项目的隐含约束；新项目需要的机器计划格式在实际需求出现时再定义。
