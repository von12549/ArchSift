## 用户操作流程

1. 选择真实目标、entry、TFM、Configuration，并选择“建立外部经审查项目证据”。显示实际 Git 状态、项目范围、受保护源根、工具绝对路径/哈希及已有证据。
2. 选择源根外的证据目录和本地 feed。生成具体执行预览，包括快照路径、restore/build 参数、子进程环境、imports/自定义任务风险以及 NuGetAudit 覆盖值。用户启动该具体构建任务，授权只针对显示的范围。
3. UI 进行安全基线、输入清点和 capture，建立同字节快照并 restore。实际新增输入使本次状态回到“需补捕获”，完成 capture 后才进入构建。准备阶段的 restore 材料需要生成/读取关系，不能冒充构建成功。
4. 执行 build，退出 0 后逐项目 ResolveReferences。展示成功项目数、owner、TFM/Configuration、选择的编译/实现引用和追踪输入；失败保留日志并停在失败阶段。
5. 审查页展示成功构建因果关系和全部 unknowns。审查者阅读实际材料，填写身份、理由、生成输入关系、imports/任务风险判断及边界，然后明确批准 review v2。只有具备授权的审查者可以批准；Agent 受托审查须显示授权范围和身份，不能冒称用户审批。
6. Core seal 采用 create-new；随后执行独立 validate，展示 sourceBound、owner/context 数和证据闭包完整性。失败不提供“接入为当前有效证据”操作。
7. 显示新旧配置差异，默认导出新的外置配置并选择该副本运行。原 profile、rulesets、registry entryIds、Chains、报告和版本载荷保持受保护。修改原配置或政策采纳属于独立、具体的操作。
8. 执行规则验证，在 Chain 顶部直接查看 pass/violation/inconclusive/error/not-applicable 总数、finding 及条目完成情况，按需展开下方 ruleset；同时保留证据完整性与 execution/compliance 的独立展示。
9. 从 History 查看本次及以前的运行结果，按明确的执行时间识别记录，点击恢复当时的结果与来源。用户完成最终 UI 操作/可用性确认；系统记录观察，不自动填写人工验收。

## History 与 Chain 结果展示

以下三项为用户在本次 UI 验证后明确要求纳入 0.8.0 的改进。当前源码中 Workbench 以进程内 ConcurrentDictionary 保存 jobs，列表 API 不返回时间，完成任务的内存记录最多保留约 20 项；historyList 显示状态、operation 与短 ID。renderChainJob 顶部显示 execution/compliance/exit code、项目和条目数，规则结果位于各 ruleset 卡片，未提供状态计数总览。既有 chain summary 已包含 entries[].ruleResults 和 runMetadata.startedUtc/elapsedMilliseconds，可作为历史时间与汇总的实际依据。

### 跨会话 History

History 默认加载当前配置报告目录中的既有结果，合并本会话的正在执行及已完成任务。支持读取以前 UI 和 CLI 保存的报告；刷新页面、Safe shutdown 后重开 UI、重启服务或重新进入同一配置，都能查看此前结果。允许登记/选择同一项目的其他历史报告目录，例如本次 CLI 的 reports 与 UI 的 ui-reports；读取范围限于已配置/登记的目录，显示来源路径与目标/config/profile 信息，防止把不同项目结果混在一起而无法识别。

建立持久的轻量 History 索引，并可由真实报告重建。历史结果从已落盘的 report/chain-summary/comparison 材料加载，列表分页、默认按执行时间倒序，可按 operation、Chain/ruleset 和结果状态筛选。live job 与同一持久结果合并为一项；Chain 主运行显示一项，其子 ruleset 在详情展开，避免重复成多项历史。记录身份绑定 run/artifact 及来源，不能只靠 ruleset 名或最新文件名去重。

历史查看保留当时工具版本、目标、规则/输入身份、执行结论及 coverage；不自动重跑、不更改当前配置、不写入原 profile 或重写旧报告。历史 sourceBound 表示当时的证明，当前新鲜度另行标示为未复核/陈旧/已验证，不能把旧 pass 显示成当前源码已通过。旧 schema 缺字段、报告丢失/损坏或索引失效时，显示该项的具体诊断；其他历史仍可查看。内存任务数量上限不能导致磁盘历史永久消失。

### History item 执行时间

每项直接显示实际执行开始的完整日期和时间，默认使用用户当地时区并标出时区/偏移，例如本次 A 为“2026-10-13 14:37:31 UTC+11”，B 为“2026-10-13 14:41:53 UTC+11”。同时可显示耗时与完成时间；详情保留原始带偏移时间/规范 UTC，切换显示时区不改变排序或记录身份。

优先使用保存的 runMetadata.startedUtc 等执行时间，而非用户点开 History 的时间或文件修改时间。新任务持久化 created/started/finished 时间与单调计时耗时；排队、运行、失败和取消分别显示其实际阶段。既有报告仅有 start+elapsed 时，完成时间可以明确标成推算值；旧报告无可靠执行时间则显示“执行时间未知”，不得把 mtime 当执行时间或编造日期。列表、结果详情和下载结果的时间语义应一致。

### Chain 顶部汇总

在 Chain 标题和 execution/compliance/exit code 附近加入始终可见的汇总，先看整体，再展开 ruleset。至少显示条目总数/完成数、缺失或无效/失败/跳过条目数、已记录的规则执行总数，以及 pass、violation、inconclusive、error、not-applicable 五种状态计数和 finding 总数。执行错误/条目诊断与规则 error 分开计数，不能把没有报告的失败条目当成零规则成功。

本次结果应直接呈现如下信息，无需手动相加：

| Chain | Ruleset 条目 | 已记录规则执行 | Pass | Violation | Inconclusive | Error | Not applicable | Findings | 整体结果 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| A | 4/4 完成 | 182 | 182 | 0 | 0 | 0 | 0 | 0 | partial / compliant / exit 4 |
| B | 1/1 完成 | 406 | 406 | 0 | 0 | 0 | 0 | 0 | partial / compliant / exit 4 |

计数以该次保存的各条目 ruleResults 为准，按 entryId 与 ruleId 的执行记录求和；同名 ruleId 在不同 ruleset 的独立执行不作全局去重。UI 列表过滤、排序或收起明细不改变汇总；finding 数与 violation 规则数分别展示，一条规则可有多个 finding。运行中/取消/失败时只汇总已产生的真实结果，标注“已完成部分”及缺失条目；已知计划规则数可展示为已完成/计划总数，旧记录无法知道时保持未知。

同时展示来源绑定/覆盖摘要，但项目、owner/context 数按共享输入中的唯一身份计算，不把四个 ruleset 的 105 项目累加为 420。所有相关条目均有证明才显示整体 sourceBound=true；来源/coverage 混合或缺失时显示具体比例或混合状态。182 pass 或 406 pass 不覆盖 partial 提示，也不把取消/失败变成成功。总体、状态分项与下方明细应能相互定位。

汇总采用 Web/CLI/HTML 共用的确定性投影规则，并用于实时结果、History 和导出 HTML。既有 JSON 能准确推导时不改写历史文件；若新增持久 aggregate 字段，则通过正式 Contracts/schema 演进绑定其统计范围和与明细的一致性，避免三种界面各自算出不同总数。

## 状态流转

建议状态为 Planned → Inspecting → Capturing → SnapshotReady → Restoring → InputsNeedRecapture 或 Building → Evaluating → ReviewRequired → ReviewApproved → Sealing → Validating → Validated → Configured。Failed、Cancelled、HostDrift、Stale 和 ReviewRejected 保留所属阶段及尝试编号。

InputsNeedRecapture 必须说明新增/改变输入和失效范围，生成新的 capture 后重新建立构建证明；不能只改旧 capture 哈希。ReviewApproved 固定一组材料字节，之后材料变化立即撤销其有效性并新建审查版本。Validated 仅代表当前输入和配置下的绑定；规则报告执行独立状态机，不能把 review approval、sourceBound 或零 finding 当作完整架构合规。

## 后端需求

保留 0.7.0 已有 capture/review v2/manifest v3/validate 契约，提取可复用的 EvidenceJobService、InputPlanner、SnapshotBuilder、ExternalBuildRunner、ProjectEvaluator、ReviewStore 和 ArtifactStore。Web/CLI 调用同一服务，Core 不依赖 Guard、安装/profile 或 UI 状态。建议新增的 evidence jobs API 名称仅为设计草案；正式路由应随 Contracts 设计审查确定。

任务记录持久化 job id、attempt、阶段、命令参数数组、显式工具路径/哈希、SDK/TFM/Configuration、来源、时间、父子材料关系、退出码、超时/取消、host equality 和 input identities。接口返回材料引用与摘要，避免把整份 13K 输入或 5K 材料 JSON 放入浏览器 job 轮询。Web 使用 typed request/response 和阶段允许动作校验，拒绝阶段跳跃、重复审批和客户端伪造成功退出码。

InputPlanner 同时追踪源码捕获范围、实际 SDK/resolver/imports、离线包逻辑、生成器/任务、实际 Csc 文件参数、额外文件、环境键和 restore/build 的生成输入。环境仅保存值哈希或任务定义的非秘密常量；不保存原始宿主 PATH、token 或秘密。日志需有结构化脱敏及可核查完整性策略，二进制 trace 的环境与嵌入源码风险必须在发布实现前解决，不能用普通文本正则假装完成 binlog 脱敏。

ProjectEvaluator 对每个发现项目执行 ResolveReferences，并保存全部 ReferencePath 和 ReferenceCopyLocalPaths，以及实际 MSBuildProjectFullPath、TargetPath、AssemblyName、TargetFramework、Configuration 和 capture.propertyNames。实际编译命令输入另外绑定，覆盖 ResolveReferences 后添加的 SDK/xUnit 生成源码。引用来源区分当前第一方、预捕获外部文件和本次生成文件，列出版本/culture/token/哈希；portable、RID、卫星资源和 native/data 边界沿用 v3，不扩张为运行时认证。

## 来源与新鲜度展示

证据详情持续显示目标绝对路径、capture 源身份、Git 状态（作为辅助背景）、构建快照身份、SDK/工具版本、TFM/Configuration、环境哈希、外部 input/material/DLL 哈希、reviewer 和批准范围。对 imported 文件、source generator 输出及每个 owner 提供“谁生成、谁读取、哪份 trace 证明”的追溯入口。

在接入配置、每次规则运行及恢复旧会话前重新验证。源文件、.editorconfig、props/targets、项目集合、外部 SDK/包/引用、环境输入或材料变化显示具体差异并标记 Stale。单纯年龄、文件 mtime 或 Git HEAD 相同不足以证明新鲜；仅规则库变更时可在重新 validate 后复用证据并生成新报告。显示 sourceBound=true 与 architecture partial 可同时成立的理由。

## 审查责任

机器检查项目唯一归属、字节身份、命令真实退出、求值一致、PE/闭包、材料完整和 unknowns 门禁。审查者负责外部构建确由这些输入生成这些 DLL 的因果判断、生成器/任务读取关系和不受自动捕获覆盖的风险。approved/inputsComplete 只有实际审查完成才可为 true；unknowns 不允许系统清空，须逐项解决并记录原因。

本次委托式 Agent 审查可作为一种角色，但必须有授权记录、真实 reviewer 身份和材料审查理由。UI 不默认代理人工审查；最终独立人工验收的观察保持独立，不能从自动测试、CLI 结果或一次批准推导。

## 失败恢复与取消

每阶段输出使用临时文件写入后核验，成功提交不可变材料；seal 继续 create-new 原子发布，不覆盖旧 manifest 或旧成功报告。失败尝试永久关联日志与输入，用户可以选择复用已验证材料或创建新尝试。若执行参数、环境或输入变化，按依赖图使后续阶段失效；复用 restore 缓存须再次核验，不能把缓存存在解释为 restore 成功。

后台进程必须登记 owner pid、启动身份和任务目录；Windows 以 Job Object 或等价 owned tree 回收机制防止孤儿进程，不能只按进程名批量 kill。取消先请求停止，再等待、终止所属树并确认退出，最后归还 Worker metadata leases/文件句柄，才标记 Cancelled。UI 按钮必须区分“取消中”与“已取消”，失败回收保留错误，不显示正常完成。服务/浏览器断开与任务结束是不同事件；恢复会话须读取服务器终态，不能沿用客户端成功缓存。

## 宿主与原件保护

在安装/构建/可启动 dotnet 的操作前后、每个相关阶段、cleanup 和会话结束比较 User/Machine 全环境、当前进程 PATH 及 PowerShell Profiles。只保存哈希，进程内逐字节比较。任何意外变化进入 HostDrift，停止所有后续 Guard/构建/分析命令，保留证据并要求人类处理；无自动 PATH 修复、setx、持久环境写入或 profile 编辑。

DOTNET_CLI_HOME 和 DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0 必须在同一子进程设置，禁止传播到父进程或宿主。工具使用明确已核验路径；网络默认关闭。源码根只读，snapshot 不是安全沙箱，必须先检查自定义构建逻辑。拒绝输出/快照覆盖目标、重解析链接、路径越界；证据和库副本落在源根之外。只回收精确登记的 owned 临时目录，清理前核对规范绝对路径，不删除整个仓库或历史证据。

## 证据存储与升级/清理保留规则

### 默认位置、身份与自定义目录

默认以明确选定的 ArchSift 安装/数据根为基准，按 `ArchSift\evidence\<项目标识>\<运行标识>\` 保存一次取证的整套材料；正式 manifest 固定为该运行目录下的 `assembly-manifest-v3.json`。例如安装根为 `D:\IFX-10-Root\ArchSift` 时，默认路径为 `D:\IFX-10-Root\ArchSift\evidence\<项目标识>\<运行标识>\assembly-manifest-v3.json`。`ArchSift` 指安装/数据根，不指 `D:\ArchSift` 产品源码仓库；不根据 cwd 或当前 `versions/<version>` 自动猜测。直接 ZIP/CLI 没有已选数据根时，要求显式选择数据根或自定义证据根，不回落到源码目录。

项目标识是已登记的稳定项目身份，登记时绑定规范化目标根和入口，保存原始路径与身份映射；显示名只作标签，不能用同名目录或 ruleset 名作为唯一键。运行标识为每次新取证生成的唯一 ID，记录创建/开始/结束时间、工具版本、输入身份和 attempts；不得只用日期或 latest 文件名。项目搬迁须显式重新登记/关联并重新验证，不能因名字相同自动接上旧证明。标识作为单个安全路径段校验，拒绝分隔符、路径穿越、保留名称及碰撞；运行目录 create-new，重捕获/重取证另开运行，阶段失败重试另开 attempt，不覆盖旧材料。

允许 UI/CLI 为项目或本次任务显式指定自定义证据根，仍按 `<自定义证据根>\<项目标识>\<运行标识>\` 建立运行目录。相对配置路径以配置文件目录解析，CLI 显式相对参数以 invocation cwd 解析；运行前显示解析后的绝对根、最终 manifest/快照路径、可写性与保护范围，持久保存实际选择。配置副本的 assemblyManifest 指向这次已 seal 且独立 validate 通过的具体文件，不指向可变的 latest；History/任务记录持久引用其实际根与运行身份，不在重启时改回默认目录。

默认与自定义目录均必须在分析目标和 ArchSift 产品源码根之外，且不得位于版本载荷、配置/规则/报告等受保护目录内或与它们重叠；检查规范绝对路径、现有父目录、重解析链接和包含关系，拒绝越界及已有冲突。目录不可写、空间不足或自定义目录失联时报告具体失败，不静默换根。自定义目录登记并不使整棵目录成为工具可删除的资产，也不授予修改外部 profile 或现存材料的权利。路径配置由 Contracts/Core 共享，Core 接收解析后的路径，不依赖安装器、Profile 或 Web 生命周期。

### 整套证据与不可变性

运行目录同时管理 capture、源根外同字节 snapshot、restore/build/ResolveReferences 的命令与退出记录、imports/编译输入/生成材料、引用及第一方 DLL、实际 review v2 与理由、create-new manifest v3、独立 validate 结果、宿主哈希检查、持久任务/attempt 元数据和材料路径/大小/哈希/依赖索引。导出的配置副本记录具体 manifest 引用；规则报告仍按配置报告目录存放，运行索引保留其关联，不改变 History 默认报告目录。布局可有子目录，但不能只保存 manifest 而遗失其证明材料。

已批准 review 与已 seal 材料不可覆盖；重新 validate 的结果、失败日志和新审查版本均用新的结果/attempt 文件记录，不修改原成功结论。seal 仍 create-new。归档和保留以整套材料及引用依赖为单位，包含 validate/复核需要的 snapshot、生成材料、DLL、trace 和审查材料；不能把已被 capture/review/manifest 引用的文件当作可重建缓存删除。

外部 SDK、包、环境输入等沿用 capture/manifest 的实际来源和哈希；运行索引区分本运行拥有的文件与只读外部依赖。整套材料落盘不代表独立便携，也不保证未来宿主仍具备相同外部依赖。外部字节改变/丢失仍须拒绝当前验证，不能自动补哈希。迁移/复制后有绝对引用失效时显示不可用或陈旧，保留原字节；需新绑定的情形走新 review/seal/validate，不改写旧封存材料。

| 归档与清理失败 | 优先可恢复归档，核验整套字节/依赖并记录归档位置与状态；跨目录复制不改写封存绝对引用、不冒称可直接 validate。清理前再次核对路径/归属/引用；保留操作回执与失败材料，不把失败标完成，不删除其他项目/相邻运行或历史报告 |
