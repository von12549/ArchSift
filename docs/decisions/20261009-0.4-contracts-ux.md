# 0.4.0 contracts and workbench design

Date: 2026-10-09 (Australia/Sydney). Engineering freeze for 0.4-A; D1–D6 and the user's UI requirements are authoritative. No IFX policy adoption or C/D/E coverage.

## Storage and identity

`rulesDirectory` retains its existing meaning. Managed saved JSON files remain directly in that directory. `.archsift-library.json` is a schemaVersion 1 registry of `{entryId,fileName,rulesetId,deleted}`; entry IDs are lowercase 32-character GUIDs. Existing managed files receive an entry ID when the registry is first initialized. External `config.rulesets` files are never enrolled. Delete marks a tombstone and removes only the selected managed file. Reimport creates a new entry ID, including when the name or ruleset ID matches a tombstone. A chain references only `entryId`; changing that reference is an explicit chain edit.

`chains/<chainId>.json` contains `{schemaVersion:1,id,version,description,entries:[{entryId}]}`. Chain IDs are safe filename stems (letters, digits, underscore, hyphen); version is nonblank user metadata. A chain is nonempty, references existing active library entries at creation, and has no duplicate entry IDs. Existing dangling references remain saveable when editing metadata or order; adding a new missing reference is rejected. Saves are atomic. Library imports reject active filename or ruleset-ID conflicts before mutation, validate both schema and single-file semantic composition, and retain exact bytes, including any UTF-8 BOM. Export uses the saved file's exact bytes and never serializes the editor draft. Per-card verification freezes validated saved bytes before queuing.

## Services, CLI and HTTP

Core owns `RulesetLibrary`, `ChainStore`, `ChainService` and `ChainWriter`; Contracts owns library/chain/snapshot/summary/diagnostic records. CLI and Web use these services. No Core dependency on Web, CLI, Guard or IFX.

CLI: `archsift chain verify --config <config.json> --chain <chain.json> [--target-kind real|fixture]`. It reads the library from `rulesDirectory` or `<output.directory>/rules`. Existing `verify --config` retains composition, global duplicate-rule-ID and cross-file checks. The UI removes its global Verify action, but the API retains `/api/run/verify` for compatibility. New run requests are `/api/run/ruleset` with `{entryId,targetKind}` and `/api/run/chain` with `{chainId,targetKind}`. Run configuration is frozen separately by each job; outputs always include JSON/HTML/SARIF for these new operations.

Library API: `GET /api/library`, `POST /api/library/import/{name}` (raw JSON bytes), `GET /api/library/{entryId}/json`, `POST /api/library/{entryId}/delete`. Existing rules save/read/Markdown routes stay available; validated saves update the registry. Chain API: `GET /api/chains`, `GET/POST /api/chains/{id}`, `POST /api/chains/{id}/delete`. All use existing loopback, origin and session-token protection. Imports are local file selections; no remote URL fetching.

The library list projects active cards plus reference metadata (including tombstones) and external/read-only paths. Tombstone metadata is a saved reference, not current file bytes or a reconstructed hash. The session library directory is fixed explicitly in returned/saved UI configuration; changing it requires a restart. Confirm/discard/delete interactions use an in-page dialog with the selected identity and Cancel focus. These engineering refinements preserve D1–D6 and the existing machine report schemas.

## Frozen input and reporting

Capture source/project facts once and all available ruleset bytes before execution. Build/assembly input capture is shared once per chain when needed. A build-input identity includes captured source facts, build settings, available manifest bytes and assembly bytes; SDK/TFM/configuration/binding stay recorded in children. Verify source and build evidence hashes before and after each child. An input change stops remaining entries, marks them skipped with `global-input-drift`, and makes overall policy inconclusive unless an already effective violation takes precedence. Failure to obtain shared build evidence is represented conservatively in affected child analysis, while declaration checks can continue.

Output root: `<output.directory>/<chainRunId>/`. Write `snapshot.json` before children; each entry has its own directory `<entryId>/`. Normal analysis output lives under that entry's child run ID as `report.json`, `report.html`, `report.sarif`. A missing/invalid child writes `diagnostic.json`, `diagnostic.html`, `diagnostic.sarif` directly in its entry directory. The summary is `chain-summary.json`, `chain-summary.html`, `chain-summary.sarif`. Paths stored in child summary `reportDirectory` are relative to the chain-run root. No previous output is reused.

The new schemas freeze exact JSON fields: `library.schema.json`, `chain.schema.json`, `chain-diagnostic.schema.json`, `chain-summary.schema.json`. Existing config/rules/analysis/comparison schemas are unchanged. A snapshot retains entry source paths and null identity for missing/invalid files; no hash is invented. Each summary child contains its own execution, compliance, exit code, coverage, binding, rule results, findings, limitations, report directory and diagnostic. Rule identity is the pair `(entryId,ruleId)`, rendered as `entryId/ruleId` in summary SARIF. Project count is the single captured project count. Findings remain scoped by entry; repeated checks are not deduplicated across policies.

Roll-up priority: effective violation → noncompliant; otherwise missing/error/inconclusive/skipped → inconclusive; otherwise any compliant child → compliant; otherwise not-applicable. Execution is partial if any child is partial, failed or skipped; cancellation overrides execution to cancelled. Exit 0 means fully completed, 2 global configuration rejection, 3 global execution failure, 4 partial/inconclusive, 130 cancellation. Findings do not enable fail-on. Cancellation preserves completed children and marks remaining children skipped; a cancelled audit summary remains downloadable.

Summary SARIF 2.1.0 has one run per analyzed child, qualified rule IDs, original genuine locations, and a separate orchestration run with execution notifications for diagnostics/skips/limits. Only real findings populate results. Diagnostic SARIF has empty rules/results and error notifications. Official OASIS schema validation is required for examples and actual outputs; the existing independently stored schema is used offline.

## Workbench design

Use a light engineering workbench with a navy section rail, white content surfaces, blue actions and separate semantic status badges. Tokens: ink `#17324d`, canvas `#edf3f8`, action `#155bc0`, compliant `#146438`, warning `#8a4b00`, violation/error `#b42332`. Borders and labelled headings carry section meaning; color never replaces text. Typography uses the locally available Segoe UI family for controls and Cascadia Mono/Consolas only for file identities and JSON. No external fonts or decorative motion.

Desktop layout, left aligned:

```text
ArchSift                              Language | Safe shutdown
Target configuration | Rulesets | Chains | Results | History
Selected section: configuration OR library/editor OR chain editor
Current job: target + selected card + execution/compliance badges
Summary -> rule results -> findings -> coverage -> projects (expand)
```

Use section tabs to avoid five competing full-height columns. Ruleset cards display saved/dirty state and explicit Verify/Edit/Export JSON/Export Markdown/Delete actions. Expanded detail holds rule/exception lists and file/hash identity. Chains show ordered saved entries, missing warnings, Edit/Delete/Verify Chain. The chain editor chooses existing library entries and provides explicit reorder controls. A missing reference never disables Verify Chain.

Narrow screens stack controls and cards, preserve labels and keyboard focus, wrap paths, and allow table content to scroll within its region. Summaries lead with the current scope and separately coloured execution/compliance badges; partial/inconclusive/missing/error/cancelled and coverage counts stay visible. Long details default collapsed. History has its own labelled selection; it never becomes current because of polling or filtering. Start, config failure, polling failure, and view switch use one reset function, including cached projects, counts, filters, title and downloads. Cancelled current downloads explicitly say Cancelled.

English is default; a local browser locale switch selects Chinese. Product text has stable translation keys, English fallback, unchanged machine identifiers and untouched user-authored strings. Locale rerenders presentation only and does not restart jobs or alter downloaded bytes. Current product docs and generated prose are English; historical evidence stays unchanged.

## Acceptance fixtures

Schema examples cover single ruleset, two entries, partial/compliant, invalid and missing followed by success, cancellation, import conflict, and separate SARIF findings/notifications. Behavioral tests must additionally prove reorder invariance, duplicate rule IDs across independent entries, exception scope, zero-match semantics, frozen saved bytes, deletion/reimport without rebinding, immutable input drift, CLI/UI parity and no stale current data after failed config/filter. The visual matrix covers desktop/narrow, English/Chinese and all significant result states. 0.4-F real IFX acceptance remains operator-driven, with verified package bytes and final host/process/listener audits.
