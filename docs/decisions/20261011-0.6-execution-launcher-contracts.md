## Executable contracts and versions

Contracts `ChainRunOptions.MaxConcurrency` defaults to 1. Schema rejects integers outside 1–4, nonintegers, strings, duplicate keys and unknown fields. CLI uses `--max-concurrency`; Web chain requests use `maxConcurrency`; policy/config schemas remain unchanged. B initially executes serially; E implements actual 2–4 scheduling. Intermediate candidates must not claim parallel support.

Preserve original bytes of `chain-summary.schema.json` v1. Separate `chain-summary-v2.schema.json` constrains schemaVersion 2 and requires `executionOptions` in snapshot. B emits new v2 ChainSummary; old v1 remains deserializable/validated as v1 without invented concurrency/timing. Progress is a separate schemaVersion 1 snapshot, never mixed into final findings. C adds optional v2 `preparation/evidence/evaluation/inputVerification/reportWriting/total` millisecond timings; end-to-end evaluation may include child verification, so documented overlaps are not summed as total.

Core synchronously emits `ChainProgress`; host binds jobId and atomically retains the latest snapshot. Generate runId before preparation, revision increases monotonically, and copy entry arrays for each publication. endedCount counts all terminal states; executedCount only completed/partial (including noncompliant), skippedCount only skipped, runningCount running/writing. Failure/cancellation remain visible entry states, not successful execution. outputAvailable means this run's complete child report/diagnostic exists, not policy compliance. Job termination follows successful final-summary writing.

Stage/entry/cancellation/drift semantics follow formal-plan section 3. Rule-library edits after byte freezing do not change current policy; source/build drift revokes affected binding. Acquire job gate before creating/preparing jobs so busy requests cannot scan new targets. Save chain definition and saved ruleset bytes at submission; discover source inside preparation. Cancellation before source exists emits skipped audit, never zero-project success.

## Launcher host boundary

Web host serves a separate loopback launcher and owns one Workbench Web child. CLI `launch --root` is its outer lifecycle parent. Launcher reuses Setup read-only package/install verification; Setup never depends on Web and Core never references profile/Setup. Permit explicit Web→Setup shared verification, with no new package dependency; architecture checks must allow this host reference.

Metadata: `config/profiles.json` and `config/selection.json`, independent schemaVersion 1; new managed file `config/default.json`. Catalog limit 100 entries/install, each JSON <=4 MiB. Paths/profileIds unique; default references a registered entry. configProtected/libraryProtected are SessionProfile/list projections after reading install state, never self-declared persisted protection. Do not merge different paths by equal names/bytes.

Launcher and Workbench enforce loopback/origin/session-token, CSP and body limits. Launcher APIs: GET state; POST register (name/configPath/expected catalog hash), create (name/configPath/config/expected catalog hash), start (profileId), stop, shutdown. Validate fields/hashes for all mutations; reject start during incomplete exit. Register/create display full paths and JSON review. External JSON is read-only; create only uses free nonmetadata paths inside configRoot. Without metadata and with one valid managed config, explicitly preview initialization then ask user registration confirmation; GET/smoke never writes implicitly.

D refinement: read-only POST preview resolves new JSON relative paths against its intended config directory; show complete preview before create. start also verifies catalog/config/selection hashes. Reject unknown selection schema without overwrite at startup. Workbench reports unsaved sections. Launcher close explicitly reviews discarded session changes and always rejects active jobs. Private profile messages use compact single-line JSON plus stdin-v1 lifecycle, not multiline JSON as a line protocol. Both hosts fix Production and bundled wwwroot, avoiding development static-asset maps as external package dependencies.

Verify install identity/profile bytes before explicit-array launch of selected-version Web. Pass URL/token through memory callbacks, never logs/metadata. API Workbench addresses stay private to the session, never persisted. New Workbench receives SessionProfile via anonymous private stdin startup message; stdin EOF/shutdown then controls parent lifecycle. Environment contains only channel identity, no JSON/token. Explicit ui --config retains its visible URL line.

Before switching, user resolves jobs/unsaved edits in the old Workbench. Launcher queries private readiness/shutdown. Old Workbench presents unsaved-form decisions; absence of active jobs never automatically discards edits. Start new session only after old service fully exits. Parent exit/cancellation drains current audit; timeout terminates only the exact owned process tree.

Explicit compatible families are 0.4.0/0.5.x/0.6.x with config/library/chain schema 1; unknown families/schemas rejected. Separate installation integrity from config health so missing JSON does not block launcher display. Preserve profiles/selection bytes without treating them as single ConfigPath receipt state. Whole-config-directory backup does not establish multi-profile protection.
