# Reviewed external-build evidence (0.7.0)

## Per-project context evidence (manifest v3 / review v2)

For targets whose projects actually select different versions of same-name dependencies, use `evidence capture ... --context-model project` to generate an unapproved review v2 template. The build snapshot must match captured current source bytes. Build and per-project evaluation take place outside source. Each project's evaluation command must include `-t:ResolveReferences -getProperty:MSBuildProjectFullPath,TargetPath,AssemblyName,TargetFramework,Configuration,<captured-propertyNames> -getItem:ReferencePath,ReferenceCopyLocalPaths`. Retain actual output as evaluation-trace material and review successful build logs/generated inputs.

Specify buildSnapshotRoot and, for every projectContexts entry, its stable id, sourceProject, actual assemblyPath, evaluationPath, **every evaluated ReferencePath.FullPath** and explicit `dotnet-reference-path` policy. Each discovered project must have exactly one primary owner. Reference files must remain readable at validation. Framework/external references must be captured beforehand; first-party dependencies must match current DLLs from the same build. review.assemblies lists first-party owners only. Global frameworkPaths may be empty because actual framework selection is in each context's referencePaths. Unknown inputs or unresolved references cannot be approved.

`evidence seal` produces v3, then `evidence validate`, ordinary verify and chain verify reuse its proof. Names/culture/tokens must match within each context; selected versions must be at least the requested version and bound to actual evaluation. No directory scan guesses the highest version. Old v1/v2 retain strict exact-closure verification. Workers read each context's metadata and count only its owned first-party source. They execute neither assemblies nor test entry points and do not prove arbitrary runtime dynamic loading. Reports show project-contexts, context count and external review provenance; declaration-model limitations and overall partial/exit 4 may remain.

When implementation dependency completion is needed, put every `ReferenceCopyLocalPaths.FullPath` into optional `runtimePaths`; do not guess through directory scanning. Every file still requires pre-build capture or proof of generation in this build. Portable compilation uses actual managed assets without a RID qualification. Other RID candidates, satellite resources and native/data files retain hashes but are not selected as neutral managed assemblies and do not prove deployment RID/dynamic loading. Compatible actual copy-local implementations may replace non-SDK compile references. Token-bearing requests require exact token equality; tokenless requests permit a proven strong-name selection. Old v2 exact-identity rules remain.

Recursively check each owner's static implementation closure. A Worker can batch contexts only when every shared simple-name selection has identical DLL identity/bytes and owner names are distinct. Results still retain stable context identity per owner. Contexts with version conflicts remain isolated.

The process client assigns a unique metadata lease to each Worker. After child exit, the parent verifies paths/links and reclaims that lease, preventing live metadata handles from blocking deletion. Failure/cancellation first terminates and waits for the child, without touching other reports, targets or original assemblies. Cleanup failure remains an error.

Capture and older evidence retain their 4 MiB limit. New v3 manifests/review v2 and each evaluation JSON are limited to 16 MiB. Check size/material structure before parsing evaluation JSON; do not remove references/materials to fit the limit. Full contracts and stage gates are in `docs/decisions/20261012-0.7-project-context-closure.md`.

## Single-closure evidence (manifest v2 / review v1)

For existing mode, assembly-manifest v2 marks `external-reviewed`. ArchSift verifies input/material/DLL/dependency identity. The operator uses actual build records to review the causal claim that these inputs successfully compiled these DLLs. Complete JSON or one aggregate hash does not establish build authenticity. Conservative v1/isolated limitations remain compatible.

1. Create an evidence directory outside the target root. Configure existing mode with explicit TFM/Configuration. First review external snapshot build commands, offline restore sources, generator/task risks and output paths. Do not execute target entry points.
2. Prepare `external-input-paths.json` as a string array of absolute paths for actual SDK tools/imports, framework DLLs, external imports, generators/tasks and their additional file inputs. Files already captured inside target source need not be duplicated as external inputs. Uncaptured nonstandard in-source inputs must enter a reviewable input plan; do not approve an incomplete set.
3. Before building, run `archsift evidence capture --config config.json --inputs external-input-paths.json --output <evidence-directory>/capture.json`. The tool computes source/build/external-file identities and hashes environment values for properties referenced by declarations, without printing raw environment data. If SDK/import/generator/task logic reads other keys, capture them using `--environment-inputs <environment-key-name-json-array>` and validate their hashes later. Missing inputs remain unknown and require a new capture/build. It also creates an initially unapproved `capture.json.review-template.json`.
4. Run the reviewed explicit commands on an external snapshot made from captured inputs. Record successful exit codes, SDK/TFM/Configuration, argument arrays, actual MSBuild inputs/evaluation traces and logs. Evidence must cover restore-generated assets, package build logic, SDK imports, custom inputs and every project. Discovering new external inputs after building requires a new capture/build. Never seal a failed/incomplete build. A snapshot is not a security sandbox.
5. Fill the review template with the actual reviewer, sdk and sdkToolPath (MSBuild.dll in the SDK directory; capture `.version` beforehand too), commands, exit codes, each project's evaluated assembly/TFM/properties, explicit global properties, ordered assembly source paths, framework paths, imports/generatorsAndTasks. Material roles include build-log/evaluation-trace/review-notes and generated-input. Trace restore/SDK/generator-produced assets, source/props and other files subsequently read by the build, recording content identity and generation/read causality. At least one generated-input record is required; missing inputs remain unknown. Get material identities using PowerShell `Get-FileHash -Algorithm SHA256` converted to lowercase and `Get-Item.Length`. Capture produces source InputIdentity/BuildInputIdentity automatically; do not calculate them manually. Set `approved` and `inputsComplete` true only after actual review, with empty `unknowns`. Preserve specific reasons for untraceable inputs and stop.
6. Run `archsift evidence seal --config config.json --capture <capture.json> --review <reviewed-json> --output <evidence-directory>/assembly-manifest.json`. Every DLL must be within the manifest directory or its children. frameworkPaths are actual pre-captured framework reference DLLs, not first-party analysis assemblies. netstandard/net8/net10 may each use their own exact-PE-identity framework reference surface; a newer same-name framework cannot impersonate the required version. Nonframework same-name conflicts remain prohibited, with version/culture/token checked individually. Manifests use create-new semantics, never overwrite existing files, and leave no successful manifest on failure.
7. Point configuration `build.assemblyManifest` at the seal and run `archsift evidence validate --config config.json`. Binding failure returns 4, invalid configuration 2 and material-read/execution errors 3. Subsequent ordinary verify, saved-card verify and chain verify reuse the same Core validation. Report buildContext evidenceOrigin/evidenceSha256 and inputIdentity identify this evidence and its origin.

Retain capture/review/logs/traces/review-notes, external inputs and DLLs during verify; the tool rereads and validates them. Changes to source/props, materials, environment inputs or SDK files require new evidence. Binding covers compiled type dependencies only under the captured configuration. Declaration project/package rules still report conditional-model limitations, and the overall report can remain partial. Zero matches, insufficient closure or unbound material cannot pass. Release-optimization coverage limits remain visible.

Source capture also includes implicit compiler configuration `.editorconfig`/`.globalconfig`/`.ruleset`; changes invalidate old evidence. Other uncaptured compiler inputs still require explicit tracing and cannot be approved as complete.

For real IFX, execute reviewed commands block by block according to authorization. Complete synthetic positive/negative cases first, then review the 105-project mapping and representative B01-B05/B07 fixtures. Without actual IFX evidence, do not claim 406 candidate rules passed. Preserve original installation, Class A rules, chains and historical reports, with all evidence outside target source.
