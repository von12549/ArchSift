# ArchSift Workbench architecture tests: headless gate and reports

For current package/configuration setup, use [project integration](project-integration.md), [generic templates](../samples/workbench/README.md) and [getting started](getting-started.md). The [0.10.0 release status](releases/0.10.0/release-status.json) distinguishes preparation from accepted artifacts. Historical [0.9.0-dev candidate use](lightweight-test-workbench-candidate.md), [LT06 machine evidence](acceptance/20261016-lightweight-lt06-candidate.md) and [independent human review](acceptance/20261016-lightweight-lt06-human-ui-review.md) retain their original source, scope and timing; they do not qualify new release bytes.

The Web UI provides an Architecture tests tab. Open an existing Web session against an independent target copy using `archsift-web --config <Web JSON>`, then enter the absolute path of the external `test-gate` JSON configuration in that tab. Both configurations must have the same `targetRoot`. Reading configuration only checks the original case-ID baseline, enabled JSON cases and not-included list; it does not build or test. Original IFX C# class/method names and actual results appear only in completed-run reports. Baseline IDs alone do not prove discovery or execution.

Original MTP/CTRF execution IDs may all change at a different absolute worktree path. For the historical version 1 baseline workflow, do not reuse the old path's baseline or automatically accept new IDs. Run the complete native tests at the fixed new path, confirm all 80 original names, Theory rows, three-class distribution, source files and project references remain, then save that worktree's actual execution-ID file and SHA-256. The gate checks this explicit baseline item by item; unknown/mismatched cases cannot pass. [LT05 acceptance](acceptance/20261015-lightweight-lt05-ifx-regression-measurement.md) records cross-worktree ID differences and local-baseline creation. Current portable version 2 consumers instead use their approved logical required-case manifest as described in the [portable guide](../samples/portable-ifx/README.md).

IFX-specific C# tests in the target copy remain read-only. The UI can copy JSON rules into the Web session's external rule library, then validate/save them with the Rulesets editor. It also generates a hidden external `test-gate` configuration copy for CLI use. New runs read those saved rule bytes; original target JSON is not overwritten. Full mode retains all original tests and JSON cases without case filtering. Subset mode requires an actually discovered UID, is diagnostic only and cannot allow the full gate. Web shares the existing workbench task lock and can cancel controlled child processes. Test history lists state markers/existing reports; unknown does not trigger automatic evidence collection. JSON/HTML downloads come from the current authoritative report. The complete-evidence-workbench action opens the separate existing evidence workflow.

`archsift test-gate --config <JSON>` performs explicit offline restore, normal incremental build, test discovery and complete test-project execution in the specified independent target copy. It runs existing dedicated C# architecture tests and reviewed enabled JSON type-dependency tests. CLI and Web use the same `ArchSift.TestGate` service. Full evidence collection still uses the separate ArchSift evidence workflow; the two results do not substitute for each other.

Historical schemaVersion 1 configuration explicitly supplies the absolute target path, relative test-project path, test executable name, `net10.0`, Debug/Release, in-target `NuGet.config`, local offline `localFeed`, external `packageCache`, in-target rule paths, trusted original IFX execution-ID file/hash and a fresh external `runDirectory`. IFX xUnit v3/Microsoft.Testing.Platform uses `runnerFormat: "mtp-ctrf"`; synthetic native xUnit-event projects use default `xunit-json`. See the [LT02A example](../samples/ifx-lt02a/README.md) for historical source integration and mechanism rules. Those rules are not formally approved Class B policy. Current schemaVersion 2 uses approved required-case inputs and rejects mixed legacy identity inputs.

In the historical version 1 example, `originalBaseline` references the [original80 actual execution-ID baseline](decisions/20261015-lightweight-ifx-original-case-ids.json). Calculate `originalBaselineSha256` from the **actual current bytes** used by the configuration. The repository LF copy's SHA-256 is `55b0f65b535516993761a0121ed4b6db26a98a698291c03056b1a85052cf3a33`. Adding/removing original cases requires separate review; additional JSON cases cannot compensate. Native MTP discovery UIDs and xUnit CTRF execution IDs are different domains. The gate verifies actual terminal IDs rather than inferring execution from display names.

Every controlled restore/build/discovery/test child receives `IFX_UPDATE_SNAPSHOTS=0`; even parent value 1 cannot update API snapshots during this gate. If `DOTNET_CLI_HOME` is isolated, the same child also receives `DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0`. Target application entry points are not executed. `filterCaseId` is diagnostic only and produces subset coverage, never complete allowance.

A completed run directory contains `architecture-test-run.json`, `architecture-test-run.html`, `architecture-test-state.json` and stage logs. JSON follows the [frozen schema](../schemas/architecture-test-run.schema.json) and is authoritative for this run's scope, actual cases, original JSON rule statuses, matched counts, findings, stages, not-included items and `runGate`. HTML safely projects the same data. If original IFX tests provide only assertion messages, no type findings or source-line numbers are fabricated. Unmigrated Class A and disabled Class B candidates retain provenance, responsible party and reason and do not count as passed. Failure to save the authoritative report returns 3 and cannot reuse an old success.

Exit codes: `0` complete pass; `2` actual assertion/rule violation; `3` execution/authoritative-report error; `4` inconclusive coverage, subset or known input changes during the run; `5` invalid configuration; `130` cancellation. `runGate` is fixed to that run's outcome. Subsequent rule/known-input changes affect history applicability only, never rewrite its original conclusion.

`archsift test-history --directory <common-run-parent> [--target <target-root>]` lists marked run directories read-only. `finished`, `failed`, `cancelled`, `interrupted` and `unavailable` remain distinct; missing/corrupt reports never show allowance. Known rule-byte/Git-commit changes produce `historyFreshness=stale`. If complete current-input equality cannot be established, freshness is unknown: even an original allow does not automatically rebuild or become a claim of current-source compliance.
