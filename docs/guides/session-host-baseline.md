# Session-bound release-harness PATH baselines

This tooling fixes the external release harness's comparison of a new command host with an old process-PATH digest. It does not alter product runtime safety checks, existing IFX policies, accepted package bytes or the historical scripts that produced original evidence. The previous Check-Original script remains immutable historical tooling. New checks use Test-SessionHostBaseline.ps1; no caller may reinterpret its result as permission to resume execution.

## Two independent gates

The original User/Machine environment and UTF-16 PATH digests plus four Profile identities/content hashes remain the persistent authority across sessions. Read the original baseline with its explicitly pinned file SHA-256. Any persistent drift stops before session approval is considered. The old Process/PATH digest stays in the old record; it is not erased, normalized or silently replaced.

A separate candidate binds the parent application/backend PID and start time, parent executable/path hashes, shell executable/path hashes and version, explicit NoProfile, working-directory hash, and reviewed launch-policy file hash. Its complete UTF-16 process-PATH hash, character count and ordered per-entry hashes are exact. A new command process may share this approved parent context; a restarted parent, reused PID/new start time, different binary, working directory or launch policy requires new human review even if PATH bytes happen to match. Temporary entries are never automatically ignored. Unsupported/inaccessible process metadata fails closed.

Candidates and confirmation receipts are new external files written with CreateNew. They never overwrite the original baseline, candidate or an existing confirmation. A receipt binds the exact candidate file digest and session ID, operator name/time and a confirmation ID. It is an operator assertion protected by local file ownership/review, not a cryptographic attestation or an independent authentication system. A matched baseline grants no execution, credential or publication authority.

## Operator sequence, not executed by preparation

No real local candidate or confirmation has been created by this implementation. Local Guard/dotnet remains stopped. The user must first authorize preparing a new session candidate; the later exact-candidate confirmation is a separate explicit human action. Synthetic CI records never count as approval for the user's machine.

1. Preserve the original baseline, diagnosis and stop evidence. Review the parent/backend context and the exact intended launch/isolation settings. Prepare a nonsecret JSON launch-policy file with schemaVersion 1, a descriptive label and an isolationPolicy description. Its hash binds the reviewed configuration; the description itself does not apply or prove environment isolation.
2. Only after user authorization, run New-SessionHostBaselineCandidate.ps1 using explicit PersistentBaselinePath, ExpectedPersistentBaselineSha256, LaunchPolicyPath and a fresh absolute OutputPath outside source. Capture occurs with -NoProfile and performs no target operation. A candidate is unapproved and cannot pass alone.
3. Review its hashes, parent identity/start time, launch settings and unchanged persistent evidence. From the same reviewed parent context/cwd, the human runs Confirm-SessionHostBaseline.ps1 with the same baseline/policy paths, CandidatePath and a fresh ApprovalPath. The command rechecks state and requires typing CONFIRM followed by the exact candidate SHA-256. There is no Force/automatic approval switch. Changed state or evidence during confirmation produces no approval.
4. Test-SessionHostBaseline.ps1 takes those paths and checks persistent state, the receipt/candidate digest, execution-context identity and exact PATH. Missing confirmation, changed context or PATH stops; it does not create a candidate/receipt, execute an operation or repair anything. Future authorized release harnesses replace their old Check-Original call with this fail-closed entry, checking it before/after operations and cleanup; they must not run the historical wrapper as a fallback.
5. Resume local Guard/dotnet only under a separate explicit user authorization after baseline confirmation. Child isolation remains child-only; DOTNET_CLI_HOME must pair DOTNET_ADD_GLOBAL_TOOLS_TO_PATH=0. Bind the actual child environment policy to the reviewed launch configuration and verify expected child changes explicitly. Never copy process PATH to persisted PATH, load/edit Profiles for repair, or silently normalize away changes.

The module exposes Compare-ArchSiftHostOperation for exact before/after checkpoints within one operation, including command-process identity. Neither session comparison nor that checkpoint routine authorizes an operation. Existing product checks already compare within one run and remain unchanged. Future external runners must separately bind their executable hashes/arguments and execution authority; this change intentionally supplies no process launcher or Guard/dotnet wrapper while execution remains stopped.

## Verification and rollback

Pure synthetic fixtures cover missing/invalid confirmation, candidate tampering, replaced persistent baseline, persistent/Profile drift before approval, restarted/reused parent identity, changed shell/launch/cwd, exact PATH bytes/order/length/temporary-entry changes, operation checkpoints and evidence overwrite rejection. They do not modify process or persisted environment. Windows/Ubuntu CI runs this suite and the existing full regression. No synthetic approval names an actual machine session.

Rollback removes the new tooling via a normal inverse PR, preserving all records and the local stop. It must not restore the historical cross-session wrapper as an executable fallback, delete a baseline or treat old product acceptance as approval of a new host context. Existing accepted 0.11.0 archives remain bound to their original source, not this tooling commit. Publishing remains a separate authorization.
